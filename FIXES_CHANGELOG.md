# Fixes applied for Railway deployment (2026-11-16)

Every item below was found by actually installing, building, booting and testing the project against a real PostgreSQL 16 database. It was then re-verified in a clean, Railway-style install (`npm ci` → `npm run build` → `npm start`, `NODE_ENV=production`, empty database).

## Deploy blockers (the app would not start or build on Railway)

| # | Problem | Fix |
|---|---|---|
| 1 | **Server crashed on start:** `Cannot find module 'express-rate-limit'`. The Workforce/Attendance module needs it, but it was not in the root `package.json` (the only one Railway installs). | Added `express-rate-limit` to root dependencies and updated the lockfile. |
| 2 | **Marketing migration 014 failed** with `role "mea_app" does not exist`, which aborted start-up on any normal Railway/Neon database. | Wrapped the grants in the same `IF EXISTS (role)` guard migration 013 already uses. The migrator accepts the original 014 checksum too, so a database that already applied the old file is not rejected. |
| 3 | **`npm run build` failed on a fresh host:** it built `client/` without installing the client's packages (vite was not found). | Root `build` now runs `npm ci --prefix client --include=dev` first, then builds. |
| 4 | **Production refused to start without Google OAuth keys**, so a first deploy crash-looped. | Now a clear warning instead of a fatal error. This is safe because setup and registration still require a Google-verified cookie, which only the real Google callback can issue (the dev bypass is disabled in production). |
| 5 | `APP_URL` defaulted to `http://localhost:4000` on Railway, which broke secure cookies and the Google redirect. | Falls back to `https://$RAILWAY_PUBLIC_DOMAIN` automatically, and warns if production runs without https. |
| 6 | A database that was still waking up killed the boot immediately. | Start-up retries connection errors only (default 6 attempts, `DB_CONNECT_RETRIES`). Real SQL errors still fail at once. |

## Application bugs

| # | Problem | Fix |
|---|---|---|
| 7 | **Help page crashed** ("Something went wrong on this page"): three Expenses Q&A entries had been pasted outside the topic's `items` list in `client/src/pages/help/content.js`. | Moved them back inside the Expenses topic. |
| 8 | Marketing Analyzer's "API offline" banner told users to "Start backend at localhost:5000", which is wrong in the merged single-host app. | Replaced with a correct message. |
| 9 | Stand-alone Workforce config was missing `port`, `isTest`, `serveFrontend`, `frontendDist`, `attendanceAdminHtml` and `CORS_ORIGINS` support. The server listened on `undefined` and test-mode rate limits never applied. | Added the missing keys. |
| 10 | The stand-alone Workforce server checked migrations in the wrong schema, so it always thought all migrations were pending and exited. | Uses the same `workforce.knex_migrations` table as the integrated migrator. |
| 11 | Workforce default `TRUST_PROXY` was `true` (trust every hop), which lets anyone spoof their IP to get around login rate limits and office-network attendance rules. | Default is now `1` (one trusted proxy, correct for Railway). |

## Tests (so `npm test` reflects reality)

- The ERP API test only created the `public` schema, while the real server needs `workforce` and `marketing` too, so 9 of 23 tests failed. It now migrates all three schemas like the server does.
- The recurring-expense tests pre-dated the required "Office 1–4" field. They now send an office.
- The legacy SQLite import test now **skips** (instead of failing) when its fixture `server/legacy/AttendanceTestApi/attendance.db` is absent. That fixture was not in the supplied archive.
- Added `sql.js` as a dev dependency (used by the legacy import scripts and their test).

**Results:** ERP 23/23 · Workforce 40/40 (+1 skipped, fixture missing) · Marketing 70/70 · browser smoke test of 25 pages with no runtime or server errors.

## Additional changes (2026-11-17)

- The Constant Expenses landing page now opens an office-based, LMS-style switch list populated from the existing Constant expense category tree. Turning on an unconfigured item opens the original `ExpenseForm` with the office and category preselected and the expense type locked to Constant; existing recurring records can be paused or resumed through their existing workflow.
- Added an admin-only **Add office / branch** action. Office names are stored in the existing `app_settings` table and are shared by the recurring form, bulk setup, switch page, recurring list, and monthly-cycle filters. Existing `Office 1`–`Office 4` values remain available.
- Monthly cycles continue to be generated by the original recurring engine, which copies the template's office into each cycle. Switching off pauses future cycles and retains historical records.
- Restored the fixed right-side module navigation and the corresponding content margins by removing a later CSS override that had converted it into a floating dropdown and removed both sidebar margins. The module menu now starts expanded for a consistent default; desktop collapse and mobile drawer behavior remain available.
- Validation for this update: JavaScript server syntax checks passed and TypeScript's JSX parser accepted the modified React files. Full Vite build could not run in this environment because the npm registry was unreachable and Vite was therefore not installed. Database integration suites were not executed because no throwaway `TEST_DATABASE_URL` was supplied.
